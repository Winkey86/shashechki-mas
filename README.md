# «Шашечки» — многоагентная система такси

Единая визуальная многоагентная система такси для четырёх лабораторных работ. Водители, пассажиры и диспетчер принимают решения, распределяют заказы и согласуют стоимость поездки с учётом тарифов, ограничений и рейтингов. Документы, отчёты и интерфейс оформляются в официальном деловом и научно-техническом стиле.

- [Постановка на все четыре лабораторные](docs/postanovka.md) — по шаблону my-task-loop, без корпоративного контекста.
- [План выполнения](docs/plan.md) — этапы, результаты и проверки.
- [Матрица покрытия требований](docs/coverage.md) — каждый критерий курса и способ его проверки.
- [Визуальная концепция](docs/design.md) и [макет интерфейса](design/interface.html) — карта, автомобили, пассажир, расчёт тарифа и раунды переговоров.

К сдаче нужны четыре отдельных отчёта, исходники и демонстрация разных режимов. Методичка допускает любую форму демонстрации; по требованию пользователя в проект входит визуальный веб-интерфейс. Полная реализация приложения в перечне требований именно к первой работе не указана. Макет содержит синтетический расчётный пример; ядро симуляции и экспериментальные результаты пока отсутствуют.

## Требования преподавателя

Источник: «Лабораторные-МАС.pdf», страницы 1–2. Тему студент выбирает самостоятельно из любой практической или исследовательской области. Обязательного списка вариантов нет.

| Работа | Что требуется |
| --- | --- |
| 1. Спецификация и архитектура | Описать задачу, агентов, роли, цели, знания, состояния, действия, полномочия, средства, каналы связи и правила взаимодействия. Построить диаграмму ролей и граф коммуникаций. Обосновать архитектуру. |
| 2. Распределение задач и координация | Реализовать и экспериментально сравнить не менее двух механизмов. Оценить время выполнения, число сообщений, стоимость координации и другие подходящие показатели. |
| 3. Переговоры и конфликты | Смоделировать конфликт интересов, дефицит ресурса или конкурирующие заявки. Реализовать механизм разрешения; сравнить поведение до и после его введения по эффективности, справедливости и соблюдению ограничений. |
| 4. Надёжность | Разработать неблагоприятные сценарии, собрать трассы, выявить отказы, ввести защитные ограничения и повторно оценить устойчивость. |

Общие условия:

- Язык, среда и архитектура свободные. LLM допустимы, но не обязательны.
- Логика агентов и ключевые алгоритмы взаимодействия должны быть заданы явно. Нельзя заменить их настройкой готового решения или вызовом готовой функции, реализующей ключевой алгоритм.
- Нужна демонстрация работы в разных режимах; веб-интерфейс приведён как пример и не обязателен.
- Нужны исходные коды и отдельный отчёт по каждой работе: реализация, исследования, результаты, выводы. Объём и форма отчёта свободные.
- Код и демонстрационные материалы предоставляются отдельно от отчётов. Облачное размещение предпочтительно, но сейчас пользователь разрешил только локальную работу.
- Если исходная архитектура не подходит для последующих исследований, её разрешается пересмотреть с обновлением отчёта №1.
- В методичке указана отправка отчётов преподавателю по почте. Это требование к сдаче, а не разрешение агенту отправлять письма.

## Наш рабочий порядок

- Двигаемся по этапам: выбор задачи → разбор → постановка → план → реализация → локальная проверка и отчёты. Переход к следующему этапу согласуем с пользователем.
- Используем локальный вариант my-task-loop без корпоративного Трекера, Вики, ALMA и обязательного spec-kit.
- Открытые решения обсуждаем по одному. Предложения в постановке утверждаем до реализации.
- Git ведём локально. Публикация, настройка удалённого репозитория, push и отправка отчётов требуют отдельной команды пользователя.
