# Tasks: визуальная МАС такси «Шашечки»

**Input**: [spec.md](spec.md), [plan.md](plan.md), research, data-model, contracts и quickstart.
**Prerequisites**: этапы 5 (валидация объёма/рисков) и 6 (команда на реализацию) my-task-loop
должны быть приняты до выполнения списка. Подготовка задач не запускает реализацию.
**Tests**: запрошены FR-051. Тесты основной логики готовились до реализации; дополнительные регрессионные и контрактные проверки добавлены при приёмке. Набор содержит 49 тестов. Документы проверяются содержательно,
автотесты, повторяющие текст, не создаются.
**Organization**: задачи сгруппированы по историям; все 92 задачи выполнены; фактическая приёмка — docs/verification.md.

## Format: `[ID] [P?] [Story] Description`

[P] — независимые файлы при выполненных указанных предпосылках; это возможность,
а не разрешение запускать дополнительные агенты. Пути от корня репозитория.
FR/SC в конце каждой задачи задают трассировку. Общие файлы изменяются последовательно.

## Dependencies & Execution Order

Setup T001–T005 → Foundation T006 (контракт типов) → US1 T007–T011 →
US2 T012–T045 (ядро и просмотр) → US3 T046–T054 → US4 T055–T067 →
US5 T068–T079 → US6 T080–T087 → Final T088–T092.

Так сначала готовятся формальная модель, схемы и отчёт №1, затем общее ядро и интерфейс,
как предусмотрено принятой постановкой. US1 не требует готовых алгоритмов или UI.
US3 использует headless-путь US2; US4 — также материализацию T047, метрики T021 и пары T050.
US5 использует US2 и переговоры US4 для F5. US6 требует US1–US5.
Все зависимости стоят раньше потребителей; полная визуальная оболочка не нужна для
независимого headless-теста US3–US5.

```text
Setup → Types → US1 → US2 → US3 → US4 → US5 → US6 → Final checks
```

Внутри фазы: контракт/тест → реализация → интеграция → фактическая проверка.
Тесты могут временно падать до реализации соответствующей функции; checkpoint требует
зелёных относящихся к нему проверок. Серии не выполняются до корректности алгоритма.

## Implementation Strategy

1. Сначала принять этап 5, затем команду на этап 6; не выполнять задачи на этапе 4.
2. Setup/контракт типов → US1: первый самостоятельный учебный результат; код ядра ещё не требуется.
3. US2: функциональный MVP с одной поездкой/картой/согласиями и сохранением.
4. US3, US4, US5: законченные лабораторные исследования по очереди, после каждого —
   проверка, реальные опыты и собственный отчёт.
5. US6 и Final checks: повторяемость, чистый запуск, доказательства и локальная приёмка.

Коммит на этапе 4 не делается. Порядок локальных коммитов реализации определяется её этапом;
push, публикация, создание remote и отправка отчётов требуют отдельной команды пользователя.
Число задач не является оценкой часов. Динамическая репутация — отделённое дополнительное
исследование: конфигурация предусмотрена, его выполнение не подменяет основные серии.
